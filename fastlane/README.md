# 🚀 Publishing the app with Fastlane

This document outlines the steps required to set up your environment, manage dependencies, and deploy the application (AAB) to the Google Play Store using **Fastlane**, plus the rules for the App Store listing.

---

## 1. Prerequisites and Environment Setup

1. 🌐 Download and install Ruby from [RubyInstaller for Windows](https://rubyinstaller.org/)
2. Add the following lines to your shell profile file (You can find your shell profile at ~/.bashrc, ~/.bash_profile, ~/.profile or ~/.zshrc depending on your system.) to ensure proper character encoding, which is essential for many Ruby gems like Fastlane:
```bash
export LC_ALL=en_US.UTF-8
export LANG=en_US.UTF-8
``` 
> [!NOTE]
> After adding these lines, restart your shell to apply the changes.

3. Install Bundler by running:
```bash
gem install bundler
```
4. Install Project Dependencies by running:
```bash
bundle install
```


## 2. Deployment to Google Play

> [!IMPORTANT]
> Before continuing with the following steps, you need to create a **Google Play Developer API** for your project and place it in the path ```../.user/VpnHoodClient/googleplay-fastlane-api-key.json```


The following command executes the `playstore` lane defined in the project's Fastfile, which handles the complete deployment process.
```bash
bundle exec fastlane playstore version_name:"YOUR_VERSION_NAME" version_code:"YOUR_VERSION_CODE" aab:"PATH_TO_YOUR_AAB_FILE"   
```

### Command Actions:
This single command performs the following critical tasks:

1. Upload AAB: Uploads the generated Android App Bundle (.aab file) to the production track on Google Play with 20% rollout.

2. Sync Metadata: Synchronizes all localized metadata (e.g., images, descriptions, release notes, screenshots) from your local project files to the Google Play Console.

3. Download Universal APK: After a successful upload, the universal APK generated by Google Play for the uploaded .aab is downloaded and saved to the following path:
> ./pub/Android.GooglePlay/apk/VpnHoodClient-android.apk

## 🍏 Publishing the App Store listing with Fastlane

The App Store listing is pushed by the `ios upload_metadata` lane (deliver), **without** a binary — the
build ships via `publish_client.yml`. Run it from the *Publish Metadata · App Store* workflow, or locally:

```bash
fastlane ios upload_metadata
```

Text lives in `fastlane/metadata/ios/en-US/**`, screenshots in `fastlane/screenshots/ios/en-US/**`
(deliver treats every subdirectory of either path as a locale, so the two must stay separate).

### The iOS listing is NOT a copy of the Android one

The Android and iOS clients do not expose the same features, and the App Store listing must show only
what the iOS build actually does. Anything the listing claims but the app cannot do is a
[Guideline 2.3](https://developer.apple.com/app-store/review/guidelines/#accurate-metadata) rejection;
naming or showing another mobile platform is a Guideline 2.3.10 rejection.

Not available on iOS — keep them out of `metadata/ios/**` and out of every screenshot:

| Feature | Why it is absent on iOS | Flag |
| --- | --- | --- |
| Split tunneling **by app** (Apps Filter page) | A regular iOS VPN app cannot enumerate or filter per-app traffic (`IosDevice.InstalledApps` throws) | `features.isExcludeAppsSupported` / `isIncludeAppsSupported` = `false` |
| **Private DNS** | No iOS settings intent for it | `intentFeatures.isPrivateDnsSettingsSupported` = `false` |
| **Kill switch** | No iOS settings intent for it | `intentFeatures.isKillSwitchSettingsSupported` = `false` |
| **Always-on VPN** | Not a user-facing iOS setting | `intentFeatures.isAlwaysOnSettingsSupported` / `IosDevice.IsAlwaysOnSupported` = `false` |
| **Quick Launch** | Android-only shortcut | `intentFeatures.isQuickLaunchSupported` = `false` |
| Any mention of **Android / Android TV / Windows** | Guideline 2.3.10 | — |

Available on iOS and safe to promote: Cloak Mode (`IosDevice.IsTcpProxySupported` = `true`), split
tunneling by country / domain / IP address / local network, custom (adapter) DNS, TCP & UDP channel
protocols, IPv4 + IPv6, and adding server keys (`IsAddAccessKeySupported` = `true`).

### App icon

App Store Connect takes the 1024 icon from the **binary**, not from deliver — there is no icon file
in `fastlane/` for iOS. It must carry no alpha channel: Apple rejects on the channel being present
(ITMS-90717), not on any pixel being translucent.
[`e2e/store-icon.mjs`](../../VpnHood.Client.WebUI/e2e/store-icon.mjs) re-encodes the appiconset to
PNG colour type 2, and refuses any icon with real translucency rather than guessing a backdrop:

```bash
node e2e/store-icon.mjs --in-place
```

## 🖼 Updating store screenshots

Every store set is generated by one script in the VpnHood.Client.WebUI repo — no client running, no
VPN, no secrets. It serves the production SPA build, answers the whole API from a sanitised fixture
([`e2e/store/fixture.json`](../../VpnHood.Client.WebUI/e2e/store/fixture.json)), and overlays a
per-platform capability patch so each set shows exactly what that OS build does. The same input
always produces the same PNG, which is what makes it CI-able.

One command regenerates every set:

```bash
cd VpnHood.Client.WebUI
npm run store:screenshots                     # build + all platforms
```

Outputs land in `test-results/store-screenshots/final/<platform>/` and are **not** committed to
this repo — dozens of PNGs per release would bloat it. The store sets are destined for the
dedicated store-asset repos (Vpnhood.App.Client / Vpnhood.App.Connect, which also hold the
fastlane metadata): `--install` copies each set into its per-locale `installDir` (declared in
project.mjs, see the table) under the install root — by default the sibling checkout named by
`INSTALL_ROOT` in project.mjs, or `--install-root <path>` for a store-repo checkout — and prunes
numbered files the set no longer produces.

Other flags: `--platform android-phone,android-tv` for a subset, `--only 3` for one screen,
`--device ipad-13` for one device, `--locale fa` for one language, `--frame-only` to re-frame
without re-capturing, `--api http://127.0.0.1:4700` to shoot a live Release client instead of the
mock (only needed for a page the fixture cannot drive).

Every set is generated in every locale listed in `LOCALES` (project.mjs) — currently `en-US` and
`fa` (Persian, which exercises the whole RTL path: rtl.css, IranSans faces, mirrored layouts). In
test-results the locale is the filename suffix (`3_fa.png`); `--install` fans each locale out into
its own store directory (the `<locale>` token in every installDir) as plain `1.png…`, and skips
locales a store does not offer — App Store Connect has no Persian, so the fa set never installs
for iOS (a `stores` override in `LOCALES` declares that).

| `--platform` | Store destination (`--install`) | Size | Look | Uploaded by |
| --- | --- | --- | --- | --- |
| `ios` | `fastlane/screenshots/ios/<locale>/` | 1290 × 2796 + 2064 × 2752 (`ipad_`) | Framed, iPhone/iPad mockup | `deliver`, `ios upload_metadata` lane |
| `android-phone` | `fastlane/metadata/android/<locale>/images/phoneScreenshots/` | 1440 × 2960 | Framed, Android mockup (punch hole) | `supply`, `playstore` / `publish_contents` lanes |
| `android-tablet-7` | `…/images/sevenInchScreenshots/` | 1200 × 1920 | Framed, tablet mockup | `supply`, same lanes |
| `android-tablet-10` | `…/images/tenInchScreenshots/` | 1600 × 2560 | Framed, tablet mockup | `supply`, same lanes |
| `android-tv` | `…/images/tvScreenshots/` | 1920 × 1080 | Bare — a TV screenshot IS the full panel; a bezel would only letterbox it | `supply`, same lanes |
| `windows` | `store/microsoft/<locale>/screenshots/` | 1920 × 1080 | App window composited on a backdrop | **No fastlane lane** — Partner Center / `msstore` CLI |

> [!WARNING]
> Google Play accepts **at most 8 screenshots per device type**. The Android sets generate 11 so
> every marketable screen exists — `--install` enforces the cap, shipping only the first 8
> (`installMax` in project.mjs) and logging what it left out.

The tablet slots exist because Play down-ranks listings without tablet assets on tablet devices;
Apple has no Android-style optionality here, but the equivalent iPad slot is already mandatory via
`UIDeviceFamily`.

deliver assigns each iOS screenshot to a device slot by its **pixel size**, not its filename, so the
`ipad_` prefix is only there to keep the two sets apart for humans; both live in the same locale
folder. The Windows composite exists because the real WPF window is a fixed 400 × 700
(`AppResources.WindowSize`) — far under the Store's 1366 × 768 floor — and its backdrop is a brand
gradient on purpose: Windows wallpaper artwork is Microsoft's, not ours to put in a listing.

### What each platform's set shows

The screen lists and the capability patches live in
[`e2e/store/project.mjs`](../../VpnHood.Client.WebUI/e2e/store/project.mjs) — that file is the one a
fork edits, and every patch value cites the device class it mirrors (`AndroidDevice`,
`AndroidDeviceUiProvider`, `WinDevice`…). Shot **array order is the store order** — filenames
number by position, so reordering a listing is moving array items. Every set opens the same way:
proof (Home connected, real speeds), the differentiator (Cloak Mode), the add-your-key Servers
page (the CLIENT model told upfront), then Protocols and the feature pages. All platforms share
the core screens (Home connected, Cloak Mode, Servers, Protocols, Split Tunneling, DNS, Proxies),
then diverge where capabilities do:

- **ios / windows** — no additions: both builds gate off app splitting, Private DNS and kill switch,
  which is also why the one fixture (recorded from a Windows Release client) serves both unpatched.
- **android-phone / android-tablet-7 / android-tablet-10** — add **Apps Filter**, a Private DNS card
  on the DNS shot, and the three Android-only feature pages: **Kill Switch**, **Always On** and
  **Quick Launch**.
- **android-tv** — the `isTv` layout in landscape; no Apps Filter and no Kill Switch / Always On /
  Quick Launch, since every one of those intents is gated on `!IsTv`.

There is no Settings-menu shot — every page it lists already has its own screenshot — and the
navigation drawer is deliberately not part of any listing.

Special shots:

- **Servers is shot empty on every platform** (`NO_SERVERS` patch): the CLIENT app ships no servers
  — users add their own key, and a listing must not suggest a bundled list (that is the VpnHood!
  CONNECT story). The page itself then renders the "add a key / consider CONNECT" guidance, which is
  exactly the screenshot.
- **Apps Filter** is fully mocked: `/api/app/installed-apps` is answered with famous apps whose
  icons are **synthesized at run time** by `prepare()` in project.mjs from the Material Design
  Icons brand glyphs already shipped as a project dependency (`@mdi/font`) — recognizable Play
  Store / WhatsApp / Chrome tiles, deterministic, and no icon artwork committed to the repo. The
  shot patches split mode to exclude Play Store and WhatsApp — "all except 2 apps", the same story
  the old hand-shot told.

Everywhere the "IP Leak Risk" chip would appear it is hidden for the capture only: an accurate
in-app caution about a user-chosen setting, but out of context on a store page it reads as a claim
about the product. The hide **fails the run** if the selector stops matching, so a Vuetify rename
cannot silently put the chip back.

Speeds on the Home shot are pinned through the API mock (`CONNECTED` in project.mjs); only ever use
throughput the product actually sustains — it is a performance claim on a store page.

### Guard rails

A capture **fails loudly** instead of shipping a broken PNG when: the page throws or logs a console
error, any dialog/overlay is open over the screen, or a `hide` selector matches nothing. Endpoints
the mock does not declare are reported at the end of the run — add them to `ROUTES` in project.mjs
when the SPA grows a new call.

Not generated (design artwork, not screenshots): `images/featureGraphic.png`, `images/icon.png`,
`images/tvBanner.png`.
